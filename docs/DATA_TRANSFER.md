# Staging → production の一回限りのデータ移行

Cloudflare Workers Builds の本番用トークンを使い、D1 `uchiwake-staging` から `uchiwake` へアプリの15テーブルをコピーする、一回限りの移行処理です。元のD1は変更しません。通常の本番デプロイからは切り離してあり、明示的に呼び出した場合だけ動作します。

## 実行前提

- 本番D1は初回ログインで作られたスペース・プロフィール・既定の負担設定だけの状態。カード・明細・支出・独自設定があれば停止します。
- ステージングと本番で同じGoogleアカウントを使用。本番だけの利用者や所有者の違いがあれば停止します。
- 両D1に最新mainの全マイグレーションが適用済み。
- 移行元に限り、旧0011で作られた `space_preferences.rent_enabled DEFAULT 1` も受け入れます。保存済みの値を全列指定でコピーするので、本番の `DEFAULT 0` と各スペースのオン・オフは維持されます。それ以外の構造差分は停止し、差分のあるテーブル名をログに出します。
- 本番ビルドのAPIトークンに、両D1があるアカウントの **D1 Edit** 権限が必要です。
- 移行中は両方のアプリで編集しないでください。エクスポート・インポートの間、D1は一時的にクエリを処理できません。

## Workers Buildsで実行

必要なら読み取り確認だけを実行できます。

```sh
npm run db:promote:staging
```

明示的に移行してからデプロイする場合は、次のコマンドを使用します。

```sh
npm run db:promote:staging -- --apply && npm run deploy:production
```

`DATA_TRANSFER_COMPLETE` と件数・一致したSHA-256がビルドログに表示されたら成功です。通常のビルド設定は `npm run deploy:production` を使用します。

同じ処理を再実行しても本番の完了記録を検出してスキップします。完了後の本番データを再びステージングで上書きしません。

## 検証と復旧

移行前に両DBを一時ディレクトリにエクスポートし、構造・参照整合性・本番が初期状態であることを確認します。実際のSQLをエクスポート済み本番のSQLiteコピーで試してから、D1に一括インポートします。本番の内容が確認時点から変化していればインポート内のガードで停止します。D1のファイルインポートが失敗した場合は変更前に戻ります。

移行前のTime Travelブックマークを `PRODUCTION_RECOVERY_BOOKMARK` としてログに出し、本番の `uchiwake_data_transfers` にも保存します。保持期限内にのみTime Travelで復旧できます（Freeは7日、Paidは30日）。復旧は本番の変更も巻き戻すため自動では行いません。

移行後に本番を再エクスポートし、全行の内容・件数・外部キーを確認します。移行元の招待情報や分類履歴もコピーし、本番の `d1_migrations` は保持します。Google OAuth・セッション秘密鍵・許可メールアドレスはD1に含まれず、変更しません。

SQLダンプ・署名付きダウンロードURL・個人のデータはログやGitに出力しません。一時ファイルは処理後に削除します。生のWranglerエラーも内容保護のため抑制します。検証失敗後は、自動復旧や手動の完了記録削除をせず原因を確認してください。
