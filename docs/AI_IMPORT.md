# Cloudflare経由のAI取り込み

## 導入前に用意するもの

1. `uchiwake-staging` Workerと同じCloudflareアカウントに、AI Gateway **`uchiwake`** を作成する。
2. AI Gatewayの **Unified Billing** にクレジットを用意する。この構成ではOpenAI・TypeSafe個別のAPIキーは不要。同じGatewayに既存のBYOK設定がある場合は、その課金経路が優先されるので確認する。
3. Cloudflareへログインした開発端末で、下記のDB移行とデプロイを実行する。アカウント情報・APIトークンをチャットやGitに貼る必要はない。
4. 実API確認用に、合計あり・合計なし・重なりのある画像・同日同店同額の別取引・返金・Amazonなど購入内容不明の例を用意する。画像、PDF、CSVの既存入力形式に対応する。

`wrangler.staging.jsonc` の追加設定：

```json
{
  "ai": { "binding": "AI" },
  "vars": {
    "APP_ENV": "staging",
    "AI_IMPORT_PROVIDER": "cloudflare",
    "AI_GATEWAY_ID": "uchiwake"
  }
}
```

Gateway名を変える場合は `AI_GATEWAY_ID` も変更する。Workers Buildsで `--keep-vars` を使用している場合は、ダッシュボードに同名の古い環境変数が残っていないか確認する。

```sh
git switch feat/luna-jev-import
git pull --ff-only
npm ci
npx wrangler login
npm run db:staging
npm run deploy:staging
```

DB移行は `0012_import_classification.sql`。分類の修正履歴・明示ルールの2表と、保存済み明細の費目編集を記録するトリガーを追加する。金額・既存の明細行は書き換えない。DB移行はWorkers Buildsの自動デプロイに含まれないので、stagingへのマージ前に実行する。

デプロイ後：`https://uchiwake-staging.tsito-apps.workers.dev/`

## 通常取り込みの担当と判断

通常の画面は `openai/gpt-6-luna` 一回で読み取りと費目の判定を行う。行ごとのJev呼び出しは行わない。Jevのしきい値を下げる変更ではなく、分類を担当するモデルと呼び出し構成の変更である。

| 処理 | 担当・条件 |
| --- | --- |
| 画像・PDF・CSV読み取りと分類 | Luna。行・出典・購入内容・明示合計・費目・判断に使った情報の種類を構造化して返す |
| 表記の正規化・合計計算 | コード。整数金額、出典、必須項目、選択可能な費目を検証 |
| 重なり | Lunaが明細番号・前後関係・位置を確認。同日・店名・金額だけで統合しない。コードも同一出典の再送を吸収 |
| 専門店 | 店名から業態・用途を特定できれば分類。ヤオコーなどの食品スーパーは食費、オートバックスなどは登録された車に対応する費目を選ぶよう指示 |
| Amazon・総合通販・コンビニなど | 店名だけでは自動分類しない。原本に引用できる購入内容がなければ要確認 |
| 明示ルール | ユーザーが保存した店名と購入内容の条件が一致した場合だけ優先適用。競合は要確認 |
| 再読み取り | 金額の差額、不明・曖昧な金額、店名・利用日の欠落があるときだけ最大1回。要確認の分類だけでは再読しない |
| 最終保存 | ユーザーが費目・金額を確認・修正し、原本確認チェック後に保存 |

Lunaの `category` は登録費目のいずれか、`basis` は `context`（購入内容）、`merchant`（専門店の業態）、`unknown`（不明）を必須とする。未知の費目・欠けた項目・不正な型はエラー。数値の信頼度やJevのnoulは生成させず、存在しないスコアを補わない。`basis` は判断に使った情報の種類であり、校正された正答確率ではない。

`context` は原文の連続した引用だけを採用する。商品を店名から推測して追加させない。既知の通販・コンビニ等の店名では、Lunaが `merchant` で費目を返してもコード側で要確認にする。購入内容に基づく回答でも引用がない場合は要確認にする。専門店と認識したか、費目を正しく選んだかというモデル自体の精度は、実入力で別途検証する。

明示された同じ請求範囲の合計だけを照合に使う。精算対象外の費目も照合には含める。合計がなければ `source_total=null` とし、行の追加・削除・修正に表示合計が追従する。日付の空白期間や件数だけから欠落を推測しない。再読で原本合計が消えたり異なる値になっても、都合のよい合計への置き換えで不一致を解消しない。金額を合わせるための創作は禁止する。

## 画面と修正履歴

- 行は実際に受信した順に、分類済みまたは要確認として表示する。全件完了を待って表示するための人工的な待ち時間は入れない。
- 読み取りと仕分けの進行表示を維持する。全行の受信が完了するまでは割合を推測せず、実際の受信・分類件数と経過時間を表示する。AIの思考文は表示しない。
- 再読が始まる場合は、具体的な金額差または曖昧な読み取りを理由として案内する。原本にない購入内容を探すためだけの再読はしない。
- 要確認には理由、以前の修正候補、該当ファイル/ページ/行と引用を表示する。金額不一致には差額を表示する。元画像を展開、PDFをダウンロード、CSVを参照できる。
- 通常の費目修正はその取引だけに適用。修正履歴は同じスペース・同じ店名の直近5件から候補を表示し、モデル入力にも自動ルールにも変換しない。
- 履歴と明示ルールは読み取り開始時に各一回取得し、行数分のDB問い合わせを行わない。
- 「今後もこの条件で分類」は初期状態オフ。保存時にだけルールを登録する。Amazon等では読み取った購入内容の具体的な語を条件にする必要がある。
- 自動分類ルールはスペース設定から削除できる。全APIで認証・所属を検証し、費目名の変更は履歴・ルールにも反映する。
- 原本とモデルの生出力はD1に保存しない。修正履歴は店名・変更前後の費目、ルールは店名・条件・費目を保存する。Gatewayへの各呼び出しでログ収集・キャッシュを無効にする。

## 呼び出しと失敗時の扱い

画面は `/api/statement/analyze` に `pipeline: "luna"` を送る。サーバーは `X-Import-Pipeline: luna` と検証済み・ルール適用済みの行を返す。ブラウザーはストリームを受信し、金額照合、必要な場合だけ一度の再読、全件完了を一つの取り込みとして扱う。通常はLuna一回、再読が必要なときは合計二回。追加の `/api/statement/classify` 要求は発生しない。

API障害、不正な回答、応答途中の切断は取り込み全体のエラーにする。要確認に置き換えて成功扱いにしたり、途中の結果を保存画面へ渡したりしない。Lunaの障害を理由に全画像を自動再送しない。中止すると進行中の受信を止め、後から結果を表示しない。

ファイル数・行数にアプリ独自の一律制限は設けていない。プロバイダー側の利用制限はエラーを表示する。再読では原本を再送するため入力・出力が増える。モデル呼び出し削減だけで初回画像読み取りの短縮を保証するものではなく、実入力で計測する。

## 取り込み診断（ステージング画面）

成功・失敗のどちらでも「取り込みの診断」を展開して結果をコピーできる。診断を表示・コピーするだけではAIを呼ばない。通常経路で使わなくなった「Jev接続テスト」ボタンは表示しない。

- `engine`: 通常は `luna`。互換経路は `jev`。
- `failure`: 失敗したモデル、工程、HTTP状態、許可した既知コード、試行回数、取得できた出典番号。
- `run`: 再読の有無とその工程で受信した件数。
- `recheck_reason`: `amount_mismatch` / `unclear_entries` / null。分類の要確認は理由にしない。
- `timing`: ユーザーの取り込み開始からの全体時間・最初の行までの時間・読み取り要求全体・読取完了後の仕分け待ち（ミリ秒）、読み取り要求数・追加仕分け要求数。通信・設定取得・解析も含む利用者視点の時間で、モデル推論のみの時間ではない。
- `classification`: 検証できたモデル判定の件数と要確認理由。再読時の判定は別評価として加算し、明示ルールの適用は除く。Lunaではconfidence/noulはnullのまま。理由は重複するため合計が要確認件数と一致するとは限らない。

店名・費目名・明細・画像・自由文・生応答・リクエストIDは診断に入れない。任意のプロバイダーコードは `unrecognized` に置き換える。サーバーログにも同じ安全な失敗情報だけを出す。ブラウザー集計の成功時間は保存しない。

## 互換性のため残すLuna＋Jev経路

旧画面のリクエストと `pipeline: "split"`、認証済みの `/api/statement/classify` は互換性のため残す。splitではLuna抽出と各行のJev要求を別のWorker呼び出しにし、最大4件並行で仕分ける。Jev待機中も読み取りを止めない。1 Workerに全行分の外部呼び出しを蓄積しない構造であり、入力件数の制限ではない。

Jevのconfidence ≥ 0.85、noul ≥ 0.9の基準は変更しない。カテゴリ・全候補・確率の範囲と合計・最大候補との一致を検証する。合計は1±0.01以内とし、境界における浮動小数点の加算誤差だけを考慮する。丸めた値で検証したり、分布を再正規化したりしない。診断の表示用 `probability_sum` は6桁、`probability_sum_valid` は未丸め値による共通の検証結果。

受信境界で `{answers: ...}` と `{result: {answers: ...}}` を同じ形式へ変換する。`success: true` は必須ではないが、内外の明示的な失敗・エラー・混在した形式・未知の入れ子は拒否する。有効なconfidence 0.78・noul 0.71は要確認。`/api/statement/test-jev` はstagingのみの固定架空サンプル一回の診断APIとして残し、接続成功は自動分類可能という意味にしない。

Jevの独立した質問にはそれぞれ費目の定義を渡す。店名・原文の購入内容・費目名はそのまま、質問と既定費目の定義は英語。修正履歴は送らない。再読しても購入内容・金額等が変わらない行は既存の結果を再利用する。要確認だけではこの経路でも再読しない。

Jevに限り429またはHTTP 500/502/503/504を最大2回再試行する。基本待機は1秒・2秒、より長い `Retry-After` を尊重し30秒超なら中断。認証・権限・残高不足、不正JSON・回答、正常な要確認、状態不明の障害は再試行しない。中止で待機も止め、復旧できなければ全体をエラーにする。

## 検証

`npm run check` でビルド、型検査、全回帰テストを実行する。`tests/luna-import.test.mjs` は通常経路の一回呼び出し、専門店と汎用店のガード、68件中65件が要確認でも再読しないこと、逐次表示、ルール・履歴、金額再読、429、不正回答、中止、診断の秘匿をモックAI bindingと実SQLiteで検証する。旧Jev経路の検証も維持する。

モックテストはモデルの実精度や所要時間を証明しない。デプロイ後は同じ画像で次を確認する。

1. ヤオコー・オートバックス等が適切な登録費目に分類され、Amazon等の店名だけの行は要確認になる。
2. 合計なしでも確認画面へ進み、要確認だけでは再読しない。診断の追加仕分け要求数が0になる。
3. 重なりの同一利用は一度だけ、同額の別利用はそれぞれ残り、返金・手数料も照合する。
4. 差額または曖昧な読み取りだけ再読し、残る不一致を具体的に案内する。
5. 通常修正から自動ルールを作らず、明示した条件付きルールのみ適用・削除できる。
6. 中止・障害で後から結果が戻らず、部分結果を保存しない。

## 切り戻し

`AI_IMPORT_PROVIDER` を `openai` にして再デプロイすると従来のOpenAI直接接続へ戻せる。この場合はWorker Secretの `OPENAI_API_KEY` が必要。DB移行はそのまま保持できる。Cloudflare経由では取り込みもレポートコメントもLunaを同じbindingから呼ぶため、個別のOpenAI APIキーは不要。
