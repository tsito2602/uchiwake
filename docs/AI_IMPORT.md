# AI明細取り込み

## 現在の通常取り込み

ユーザーの指定により、AI Gateway導入直前のコミット `d5ab87407c9e279b102abba127e22064e5a8deac` の読み取り・仕分けプロンプト・指示・推論設定を維持する。要確認の理由を表示するため、各明細に理由区分 `review_reason` とその選択指示だけを追加する。`worker/statement-request.ts` をOpenAI直接接続とAI Gatewayで共用する。

- Lunaが全ファイルを一回で読み取り、日付・店名または内容・費目・整数金額と要確認の理由区分を返す。理由のために追加のAI呼び出しは行わない。
- 原本に明示された請求合計を `confirmed_total` に返す。明示がなければ0。
- 費目はそのスペースの登録済み費目を使う。判断できない費目は要確認、内容が分かって既存費目に当てはまらないものはその他とする。
- 重複は明細番号・前後関係・位置で同一と分かる場合だけ吸収する。同日・同店・同額だけでは削除しない。返金は負数。
- Jev、追加の購入根拠判定、信頼度判定、店舗別の固定補正、履歴・ルールによる上書き、自動再読を通常取り込みでは使わない。
- 金額や行を合計に合わせて創作しない。合計の不一致や不明な費目は確認画面でユーザーが確認・修正し、最後に保存する。
- 不正な回答や途中切断、API障害を要確認の成功や部分保存に置き換えない。

新しい画面は `/api/statement/analyze` に `files`・`mode: "live"`・`stream: true` だけを送る。行ごとの仕分けAPIや画像再送は呼ばない。コードは明細の型・金額・受信完了を検証して、AIが選んだ費目を確認画面へ渡す。未知の費目は導入前と同じく要確認にする。

店名の置換辞書や、コンビニ・自販機向けに後から追加した固定分類も通常経路では使わない。これらを含め、分類は復元したプロンプトでLunaが判断する。読み取り精度・所要時間は実画像で確認する。

## 要確認の理由

`review_reason` は自由文ではなく、次の固定値から主な理由を1つ返す。理由を付けるために、分類できる明細を要確認へ変更しない。

| 値 | 意味・確認する内容 |
| --- | --- |
| `purchase_unknown` | お店は分かるが購入内容が不明。購入履歴・レシートを確認する。 |
| `merchant_unknown` | 表記から店名・支払先を特定できない。利用したお店やサービスを確認する。 |
| `multiple_categories` | 購入内容・用途から複数の費目が候補に残る。内容に合う費目を選ぶ。 |
| `none` | 分類済み、または空欄・金額の読み取り不備だけが確認理由。理由文は追加しない。 |

確認画面では費目が要確認の間だけ、理由区分を定型文に変換して表示する。店名・日付の空欄と金額0は引き続きコード側で検出する。理由がない旧形式や `none` で費目が要確認の場合は従来の案内を表示し、理由を推測しない。定義外の理由区分や自由文は不正な応答として拒否する。

理由は取り込み確認用で、DBに保存しない。既存の保存済みデータや旧クライアントを扱うため `EntryDraft` 上では省略可能だが、新しいAI出力スキーマでは必須とする。ストリーム・非ストリームのどちらも同じ区分を検証して受け渡す。

## 進行表示

ゲージと現在の処理内容・実件数・経過時間は現行UIを維持する。読み取りと仕分けを二本のゲージで表示し、全件受信までは推測の割合を出さない。受信した行はすでに費目を持ち、その件数で仕分けの表示も進める。AIの思考文は通常の画面へ表示しない。

処理中はパネル内を縦の固定領域とスクロール領域に分ける。見出し、ゲージ、現在の処理、経過時間は固定し、明細一覧だけを自動スクロールする。入力・確認画面の通常スクロールは変えない。中止すると受信を止め、遅れて届く結果を画面へ反映しない。

## 接続と保存

AI Gatewayは接続・課金の経路として維持する。`wrangler.staging.jsonc` の設定は次のとおり。

```json
{
  "ai": { "binding": "AI" },
  "vars": {
    "APP_ENV": "staging",
    "AI_IMPORT_PROVIDER": "cloudflare",
    "AI_GATEWAY_ID": "uchiwake"
  }
}
```

モデルは `openai/gpt-6-luna`。Gatewayの課金を利用する構成では個別のOpenAI APIキーは不要。呼び出しは `store: false`、Gatewayのログ収集・キャッシュ無効を維持する。APIキー、原本、生の応答、上流の自由文をログに出さない。AI呼び出しはサーバーだけで行い、全APIで認証・所属スペースを検証する。

DB移行0011・0012はそのまま保持する。今回の切り戻しにDB変更はなく、保存済み明細・履歴・明示ルールを削除しない。通常取り込みの判定では履歴・ルールを参照せず、新しいルールも自動生成しない。既存の保存・費目編集・ルール管理のデータ互換性は維持する。

`AI_IMPORT_PROVIDER: "openai"` なら従来の直接接続を使う。この経路はWorker Secretの `OPENAI_API_KEY` が必要。今回、接続設定・課金設定・productionの設定は変更しない。

## 旧クライアントの互換性

明示的な `pipeline: "luna"` / `pipeline: "split"` と `/api/statement/classify`、staging限定の `/api/statement/test-jev` は旧クライアント用に残す。新しい画面はこれらを使用しない。古い画面を開いたままの場合は更新してから取り込む。

互換経路では従来の回答検証を維持する。Jevの直接形式とresult形式の正規化、confidence 0.85・noul 0.9、確率分布の検証は変更しない。互換コードを理由に通常の取り込みで追加判定や再読を行わない。

## 検証

`npm run check` でビルド・型検査・回帰テストを実行する。

- `tests/fixtures/pre-gateway-statement-request.json` は導入直前の履歴から取得した固定のリクエスト。理由区分とその指示を除いたプロンプト・指示・推論設定・4項目スキーマが完全一致することを検証する。
- `tests/simple-statement-import.test.mjs` は理由付き68行の一回取り込み、理由3種・該当なしの逐次受信、旧形式との互換性、理由の検証・ログ非公開、追加判定・再読・履歴参照なし、費目名変更、中止、429、不正回答・途中切断で部分成功にしないことを検証する。
- 確認画面のテストで理由の出し分け、費目修正後の非表示、空欄・金額0の既存の確認事項を検証する。
- 進行表示のテストは二本のゲージと実件数を維持し、進捗表示を明細一覧の外に配置することを確認する。実ブラウザーでもスマートフォン幅で68行の自動スクロール後に進捗表示が画面内に残ることを確認する。
- 旧クライアントのJev・Luna拡張経路の回帰テストも維持する。

デプロイ後は、同じ実画像で店名・費目・合計を確認する。stagingのビルド番号で反映を確認し、読み取り・仕分け中にゲージと現在の処理が見え続けることも確認する。
